# 03. Постобработка текста LLM

Постобработка — второй, независимый этап: расшифровка уже готова, модель работает только с текстом.

## Готовые действия

| `post_action` | Что делает | Где менять |
|---|---|---|
| `none` | ничего, только расшифровка | — |
| `summary` | краткое содержание + тезисы | `backend/app/prompts.py` |
| `minutes` | протокол встречи: вопросы, решения, задачи со сроками | там же |
| `bullets` | структурированный конспект списками | там же |
| `translate` | перевод на `target_language` | там же |
| `custom` | произвольная инструкция из поля UI | `post_instruction` |

Промпты вынесены в один файл `backend/app/prompts.py` — правка текста требует только `docker compose restart worker`.

## Выбор модели

| `LLM_MODEL` | RAM | Комментарий |
|---|---|---|
| `gemma3:12b` | ~9 ГБ | **дефолт для VPS и первого запуска** |
| `gemma4:26b` | ~18 ГБ | локально на мощном GPU, Ollama на хосте (см. ниже) |
| `qwen2.5:3b-instruct` | ~3 ГБ | быстро, хватает для коротких заметок |
| `qwen2.5:7b-instruct` | ~6 ГБ | хорошо держит русский |
| `llama3.1:8b-instruct-q4_K_M` | ~6 ГБ | альтернатива |
| `qwen2.5:14b-instruct` | ~10 ГБ | заметно лучше на протоколах |
| `gemma2:9b` | ~7 ГБ | хорош в кратких пересказах |

```bash
docker compose exec ollama ollama pull qwen2.5:14b-instruct
sed -i '' 's|^LLM_MODEL=.*|LLM_MODEL=qwen2.5:14b-instruct|' .env
docker compose up -d api worker
```

### Ollama на хосте (локальная разработка)

Если Ollama установлена на самой машине (Windows: `C:\Program Files\Ollama`) и уже содержит нужную модель, контейнер `ollama` не нужен:

```env
LLM_BASE_URL=http://host.docker.internal:11434/v1
LLM_MODEL=gemma4:26b
```

Окно контекста хостовой Ollama задаётся **её** переменной окружения `OLLAMA_CONTEXT_LENGTH` (не `.env` проекта): выставьте не меньше 16384 и перезапустите Ollama — иначе она молча обрежет крупные пачки нормализации. Whisper и LLM делят одну видеокарту; если не хватает VRAM, Ollama выгрузит часть слоёв на CPU (медленнее, но работает).

## Нормализация расшифровки

До постобработки текст проходит LLM-этап `normalize` (включён по умолчанию, `NORMALIZE_DEFAULT=true`; для одной задачи — `"normalize": false` в `options`):

* расставляет пунктуацию и заглавные буквы — faster-whisper, особенно turbo, часто отдаёт русский текст без них;
* исправляет искажённые термины по глоссарию: «кавка» → Kafka, «пепельмин» → BPMN, «металл» → middle.

Работает пачками сегментов по `NORMALIZE_CHUNK_CHARS` символов (8 000 по умолчанию: меньше запросов и больше контекста для терминов; на слабых моделях уменьшите до 2 500). Лимит токенов ответа для пачки считается от её размера (`NORMALIZE_MAX_TOKENS`, 0 = авто): модель получает пронумерованные строки и возвращает их в том же виде, поэтому таймкоды сохраняются. Строку, которую модель потеряла, и пачку, на которой запрос упал, конвейер оставляет исходными. Сырой текст ASR сохраняется в `result.raw_text`.

**Глоссарий** — `backend/app/glossary.txt`, строки вида `как слышится → как правильно` или просто термин. Собран из журнала ошибок `docs/ASR-norm.md`. Свой файл: положите его в `./data` и укажите `GLOSSARY_FILE=/data/glossary.txt`.

Вторая линия защиты — подсказка самому Whisper: `ASR_PROMPT` в `.env` (или `prompt` в задаче). Пишите её связным предложением с пунктуацией: Whisper подхватывает и термины, и стиль (см. [02-asr-whisper.md](02-asr-whisper.md)).

## Длинные записи

`backend/app/llm.py` реализует map-reduce: текст длиннее `LLM_CHUNK_CHARS` (12 000 символов ≈ 12–15 минут речи) режется по абзацам, а если абзацев нет (Whisper отдаёт текст одной строкой) — по предложениям и словам. Каждая часть обрабатывается отдельно, затем результаты сводятся вторым запросом.

Контекст Ollama задаётся `OLLAMA_CONTEXT_LENGTH` (по умолчанию в compose — 16 384 токена). Без этого Ollama использует 2–4k и **молча обрезает** вход. Кусок + ответ должны помещаться в окно: 12 000 символов русского текста ≈ 5 000 токенов.

Если у модели контекст 128k и вы хотите обрабатывать целиком — поднимите `LLM_CHUNK_CHARS` и `OLLAMA_CONTEXT_LENGTH`.

## Настройка качества

* `LLM_TEMPERATURE=0.2` — для протоколов и выжимок. Выше 0.5 модель начинает додумывать факты.
* `LLM_MAX_TOKENS=2048` — потолок ответа. Для часовых встреч поднимите до 4096.
* `LLM_REASONING_EFFORT=none` — обязательно для «думающих» моделей (gemma4, qwen3): иначе весь лимит токенов уходит на рассуждения, `content` приходит пустым, а нормализация молча оставляет исходный текст. Для обычных моделей оставьте пустым.
* Системный промпт (`prompts.SYSTEM`) прямо запрещает выдумывать факты — не убирайте эту фразу.

## Диаризация (кто говорит)

Выполняется отдельным сервисом `diarizer` (sherpa-onnx: сегментация pyannote-3.0 + эмбеддинги WeSpeaker, CPU, без токенов Hugging Face). Включена по умолчанию (`DIARIZE_DEFAULT=true`) и идёт **параллельно** с распознаванием; для задачи отключается чекбоксом в UI или `"diarize": false`.

* Отрезки говорящих сопоставляются с сегментами Whisper по наибольшему пересечению; метки — «Спикер 1», «Спикер 2»… в порядке появления.
* Текст результата превращается в диалог с репликами по говорящим; в SRT/VTT метка идёт перед фразой. Нормализация и постобработка работают уже с диалогом (для протоколов это то, что нужно).
* Число говорящих лучше указать, если оно известно (`num_speakers`); иначе подбирается порогом `DIARIZER_THRESHOLD`.
* Если сервис недоступен — задача завершится без разделения, в логе worker будет предупреждение.
* Ограничение: если говорящий меняется внутри одного сегмента Whisper, сегмент целиком достаётся тому, кто говорил дольше.
